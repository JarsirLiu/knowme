# AI 文档维护规则

## 事实与方案分离

- `docs/current/` 只写已经被代码和测试验证的行为。
- `docs/design/`、`docs/proposals/`、`docs/issues/` 写未来方案、候选设计和待办
  风险，必须标明状态。
- 如果实现和文档冲突，先修正文档或代码中的事实来源，再继续扩展设计。

## 变更同步

以下变化必须同步文档：

- 新增或移动包、模块和依赖方向。
- 修改 API、SSE 事件、数据库模型或迁移方式。
- 修改 Run 状态、审批、取消、租约、恢复或上下文压缩。
- 修改 workspace、Shell、网络或设备权限。

文档应该链接到拥有该行为的源码入口，而不是复制大量实现细节。引用设计文档
时，明确它是规划而非现状。

## AI 工作输出

完成代码任务时，应说明：改了什么、为什么、验证了什么、剩余哪些风险。发现
文档与代码不一致时，应明确指出，不要默默选择对自己方便的一侧。
